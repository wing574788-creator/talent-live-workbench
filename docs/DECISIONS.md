## 2026-10-18 阶段 0

### Pi SDK 验证结论（PRD 11.2 待核实事项）

验证版本：`@earendil-works/pi-coding-agent@1.3.0`（精确锁定；`@earendil-works/pi-ai@1.3.0`、`typebox@1.3.27` 同样精确锁定）。验证代码：`apps/server/src/agent/adapter.ts`，测试：`adapter.test.ts`（用脚本化假模型，不联网、不需要 API Key），命令行演示：`pnpm agent:spike`。

| 问题 | 结论 |
| --- | --- |
| 自定义工具的导出名 | `createAgentSession({ customTools: ToolDefinition[] })`。工具形状：`{ name, label, description, parameters, execute(toolCallId, params, signal, onUpdate, ctx) }`，`execute` 返回 `{ content: [{type:'text', text}], details }`。`defineTool` 是可选的类型辅助。 |
| TypeBox | SDK 的 `Type` 只作为类型导出，运行时拿不到。需要自己依赖 `typebox`（精确版本 1.3.27，与 SDK 一致），由适配层重新导出 `Type`。 |
| 关闭内置工具 | `noTools: 'builtin'` 加 `tools: [领域工具名...]` 白名单，`session.getActiveToolNames()` 只剩领域工具（测试已覆盖）。 |
| `tool_call` 拦截在 SDK 模式下是否生效 | **生效。** 通过 `DefaultResourceLoader({ extensionFactories: [(pi) => pi.on('tool_call', ...)] })` 注入内联扩展，返回 `{ block: true, reason }` 后工具不执行，模型收到 `isError` 的结果。测试覆盖：守卫拒绝、白名单外的工具（模型调用 `bash`）都不会执行。 |
| 中止 | `session.abort()` 能中止正在执行的工具（工具收到 `signal`），之后不再继续下一轮。SSE 断开时调用它（`stream.onAbort`）。 |
| 事件映射 | `session.subscribe`：`message_update` 且 `assistantMessageEvent.type === 'text_delta'` → 文本增量；`tool_execution_start` / `tool_execution_end` → 工具事件。适配层统一转成 `packages/shared` 里的 `AgentEvent` 再推 SSE。 |
| 隔离 | 用 `DefaultResourceLoader` 的 `noExtensions / noSkills / noPromptTemplates / noThemes / noContextFiles` 关掉自动发现，避免读取 `~/.pi` 和项目目录里的扩展与上下文文件。`agentDir` 指向工作台自己的数据目录。会话阶段 0 用 `SessionManager.inMemory`，阶段 7 再换成按用户分目录的 JSONL。 |
| 假模型 | 测试用 `fauxProvider()`（来自 `@earendil-works/pi-ai/compat`），需要 `modelRuntime.registerNativeProvider(faux.provider)` 并 `setRuntimeApiKey`，否则报 "No API key found"。阶段 7 的工具调用回归测试集可以沿用这套做法。 |

遗留：真实模型（Anthropic / OpenAI 兼容 / Ollama）下的工具调用稳定性还没验证，等阶段 7 接入模型后再做；开放问题"先接哪个模型"仍待用户决定。

### 工程决策

- **pnpm 12 的构建脚本白名单**：写在 `pnpm-workspace.yaml` 的 `allowBuilds`（`better-sqlite3`、`esbuild` 允许；`@google/genai`、`protobufjs` 不允许）。原因：pnpm 12 默认不执行依赖的 install 脚本。
- **better-sqlite3 用 ^12**：Node 24 下 11.x 没有预编译包，源码编译失败。
- **`@workbench/shared` 直接导出 TS 源码**（`main: ./src/index.ts`），不单独构建。原因：前端 Vite 和后端 tsx 都能直接消费，少一道构建；以后需要发布时再改。
- **tsconfig 开启 `allowImportingTsExtensions`**：后端用 tsx 运行，相对导入写 `.ts` 后缀。
- **Tailwind v4（`@tailwindcss/vite`）+ TanStack Router 代码式路由**：阶段 0 不引入路由文件生成插件，页面少，代码式路由够用。shadcn/ui 组件在阶段 2 需要表单、抽屉时再按需加入。
- **默认端口**：后端 8787，前端 5173（均仅 127.0.0.1）；后端端口可用 `PORT` 覆盖，数据目录可用 `WORKBENCH_DATA_DIR` 覆盖，默认 `%APPDATA%\talent-live-workbench`。
- **监听地址写死 127.0.0.1**，不提供配置项（CLAUDE.md 铁律 8）。以后做局域网部署时再单独决策。

## 2026-10-18 阶段 1

- **用户手动操作的敏感改动直接生效，AI/导入的才进审核队列。** PRD 5.6 写"敏感操作只生成待审核改动"，同时写"用户手动改普通字段直接生效"；CLAUDE.md 铁律 3 明确"来自 AI 或导入的敏感改动只生成待审核记录"。按后者实现：`actor.type === 'user'` 时跳过审核（仍记日志、可撤销），UI 里用户自己点的"删除/改佣金"由界面二次确认承担把关。如果希望用户手动的删除也走审核队列，只需改 `EntityService.reviewReason` 一处。
- **新增（create）是低风险写**，AI 和导入都直接写入并记日志；AI 的"单条普通字段修改"也直接生效。AI/导入的"批量修改"（同一次多于 1 条）整批进审核；单次上限 200 条（PRD 7.3）。
- **敏感字段规则**写在 `domain/index.ts` 的各实体配置里：商品各价格、达人参考佣金/报价、合作坑位费、合作商品佣金/直播价、寄样明细单件价值；合作阶段为"完成"时任何修改。
- **变更日志存整行前后快照**（含版本号），撤销只还原前后有差异的字段。撤销的前提是记录自该日志之后未再被修改（版本号对得上），否则判冲突；撤销本身写一条新日志（`undo_of` 指向原日志），原日志标 `reverted_at`，撤销记录不能再撤销。整批撤销逆序逐条做，冲突的单独列出。
- **审核通过时再次校验版本**：提出改动时记下 `base_version`，通过时版本不一致则标 `conflict` 且不落库；`rebase` 后回到待审核。
- **乐观锁**：更新语句 `where id=? and version=?`，影响行数不为 1 即冲突；调用方也可传 `expectedVersion`。
- **没有实际变化的更新不写日志、不涨版本。**
- **查重唯一键用部分唯一索引**（`where deleted_at is null`）：平台账号（平台+账号ID）、商品款号、规格（商品+色+码）、达人-联系人关联；软删除后键可重新使用，撤销删除时若键已被占用会报"已存在"。
- **金额字段统一 `*Cents` 整数**，zod 用 `.int()` 拒绝小数；佣金率用 `real` 存百分数（0–100）。
- **样品明细（寄出/退回/核销）冗余存款号+款名+颜色+尺码**，不依赖商品行，商品改名不影响历史台账；寄样明细的 `productId` 可空。
- **drizzle-orm 升到 0.45 / drizzle-kit 0.31**：0.36 的索引配置写法与当前文档不一致。阶段 0 的迁移文件已重新生成（0000 重做），开发机上阶段 0 的空库已删除。
- **审核/日志类表也带公共字段**（铁律 9 的"所有表"），`change_log` / `pending_changes` 的 `id` 用单调递增 ULID，排序即时间序。
- **阶段 1 未做**：附件文件落盘、自定义字段值的校验与索引（只有 `field_defs` 表和各实体 `custom` JSON 列）、`import_batches` 的写入逻辑、外发日志写入——分别在阶段 2/6/7 实现。

## 2026-10-18 阶段 2

- **用户手动操作的敏感改动直接生效**（用户确认，沿用阶段 1 的决定）。**例外：合并达人无论谁发起都进审核队列**（DEV_PLAN 阶段 2 明确要求）：`requestMerge` 生成 `action = 'merge'` 的待审核记录，通过时才执行；审核时重新校验保留方和被合并方的版本号，任一方被改过就判冲突。
- **合并的执行方式**：把账号、合作、跟进、寄样/退样/核销、收货地址的归属改到保留的达人，联系人关联去重，空字段用被合并方补齐、标签取并集、回收问题次数相加，最后软删除被合并的达人。所有这些写入共用一个批次号（= 待审核记录 id），所以 `POST /api/batches/:pendingId/undo` 能整批撤销合并。
- **查重**：账号"平台 + 账号 ID"精确命中时前端禁用创建按钮、后端唯一索引兜底（返回 409）；昵称相似用归一化后的 Dice 系数（≥ 0.7，或一方包含另一方至少 2 字）只做"疑似重复"提示，绝不自动合并。阈值 0.6 时示例数据里仅共享"示例达人"前缀的昵称也会误报，所以定为 0.7，后续看真实数据再调。
- **敏感字段打码在 API 层**：达人真实姓名、联系人微信/手机、收货地址的列表和详情响应一律返回打码值，变更历史里的前后快照也打码；明文只能走 `/reveal` 接口（点击"查看敏感信息"）。编辑时未查看明文的敏感字段在表单里锁定，保存的补丁里不包含它们，避免把打码值写回数据库。
- **通用写入路由 `/api/e/:entity`**：商品、规格、平台链接、图片、达人、地址、账号、联系人、关联、自定义字段、保存视图共用一套增删改接口（实体名白名单），请求体即领域服务的输入；列表和详情是专用路由。所有路由只调用领域服务，不写 SQL。
- **列表查询的列名全部走白名单**（`searchFields / filterFields / sortFields`），自定义字段筛选的键用正则限制后以参数形式传给 `json_extract`，不拼接用户输入。
- **自定义字段**：值写入时由领域服务按 `field_defs` 校验（必须已定义、类型和选项要对得上）；列表里作为"列"出现、单选字段可筛选。未建专门索引（`indexed` 标志位已存，数据量大了再按需建表达式索引）。
- **保存视图**存在数据库（`saved_views`，按实体 + 名称唯一），内容是搜索词、筛选、排序、列显隐。
- **图片附件**落在 `数据目录/attachments/年月/ULID.扩展名`，只收 JPG/PNG/WebP/GIF 且 ≤ 10 MB，读取时校验路径不越出数据目录；第一张为主图，可改主图。
- **前端暂未引入 shadcn/ui**：阶段 2 用自写的 Tailwind 组件（按钮、抽屉、对话框、表格工具栏等，`apps/web/src/components/`），表格用 TanStack Table（服务端排序/分页）。以后需要更复杂的控件（日期选择、命令面板）时再按需引入 shadcn。

## 2026-10-18 阶段 3

- **状态校验放在领域层**（`EntityConfig.validateState`，创建、修改、审核通过时都会调用）：进入流失/放弃必须有原因；洽谈中必须有下次跟进日期；跟进状态必须在设置的选项里；合作的平台账号必须属于所选达人。前端的对话框（拖到洽谈中要日期、拖到流失/放弃要原因）只是提前收集必填项，规则本身不依赖前端。
- **写后钩子**（`EntityConfig.afterWrite`，同一事务内，撤销产生的写入也会触发）：寄样单、寄样明细、退样明细、核销变化后调用阶段自动推进。
- **阶段自动推进**（`domain/automation.ts`）：新建待寄样单 → 待寄样；寄出（已寄出/已签收）→ 已排期；开播日**过后**（严格晚于开播日）→ 已开播；已开播且仍有在外样品 → 待退样；在外归零 → 待复盘。只向前推进，来源标"自动推进：原因"并写变更日志。事件类规则（待寄样、已排期）每次都触发；时间/状态类规则（已开播、待退样、待复盘）每条合作只自动触发一次，所以用户手动改回后不会被反复推走。服务启动时和每小时各跑一次，也可以 `POST /api/automation/run` 手动触发。自动推进以默认用户身份执行（不进审核队列），因为它是确定性规则，不是 AI 提议。
- **在外数量**（`domain/sample-ledger.ts`）现在只算总数：只统计"已寄出/已签收"的寄样单，累计寄出 − 累计退回 − 核销，按款号+颜色+尺码分别计算后每项取不小于 0 再求和。阶段 4 在这里扩展按款色码的结余明细、冲抵顺序和逾期。
- **跟进次数不靠存储字段**：`cooperations.follow_count` 列保留但不再使用（恒为 0），次数、最近跟进时间、距上次跟进天数都从 `follow_ups` 现算，避免撤销/删除后计数漂移。"距上次跟进天数"按北京时间的日期差算。
- **连续"待回复"提醒**：最近 N 次跟进（按发生时间）状态全是"待回复"才提示，N 存在 `app_settings.replyStallCount`（默认 3，设置页可改，范围 2–20）。提示只出现在洽谈中的合作上，提供"转暂缓/转流失"快捷按钮。
- **跟进记录保存后同步到合作**：填了跟进状态、下次跟进日期就写回合作（走合作的校验，所以同样受上面的规则约束）；洽谈中的合作若跟进后仍没有下次跟进日期，保存被拒绝并提示补上。关联合作的跟进会自动补上该合作的达人，这样同一条记录也会出现在达人详情的时间线里。跟进至少要关联合作、达人、联系人之一。
- **跟进状态选项**存在 `enum_options`（可增删，首次读取时写入 6 个默认值，之后删光也不会自动补回）；删除选项不影响已使用它的合作。
- **看板只放 9 个主线阶段**，暂缓/流失/放弃是看板下方的三个拖放区，这三类合作在列表视图里查看；列表里阶段可直接用下拉改。拖拽用 dnd-kit（拖动 6px 后才算拖拽，点击仍然打开详情）。
- **佣金只在合作商品上**：看板卡片显示该合作所有商品的佣金范围；有商品未设佣金时标"佣金未确认"。合作商品的佣金、直播价修改（AI/导入来源）仍走审核。
- **阶段 3 未做**：联系人的"下次跟进日期"（PRD 5.1 首页"今日待跟进"包含联系人）——联系人表目前没有这个字段，放到阶段 5 做首页时一并加；跟进记录的就地编辑/删除（可在变更历史里撤销新建）。

## 2026-10-18 阶段 4

- **冲抵用"重放"而不是存分配表**：`domain/sample-ledger.ts` 每次按达人把全部已寄出/已签收的寄样明细（按寄出日期、创建时间排序）和全部退回、核销（按日期排序）重放一遍，退回和核销从最早未结清的寄出行开始扣减，得到每一行寄出还剩多少。好处是撤销、补录、改日期之后结余自动正确，不会有分配记录和流水对不上；代价是每次读取要重算，单人数据量下没有问题。**"退回时也可以手动指定冲抵哪张寄样单"（PRD 4.6）这一版没做**，需要时再加分配覆盖。
- **在外 = 累计寄出 − 累计退回 − 核销，逐款号+颜色+尺码**，只统计状态为已寄出/已签收的寄样单；待寄样单不计入。退回和核销的数量不能超过该款色码当前的在外数量，超出整单拒绝（领域层校验，前端同样提示）。
- **应寄回日期默认值**：有关联合作且合作有开播日 → 开播日 + N 天；否则签收日 + M 天；寄出时和签收时各尝试计算一次，只在还没有值时自动填，之后可手动改。**N、M 和"待寄样超过几天未寄出"预警天数都可以在「设置 → 样品寄回日期」里修改**（`returnAfterLiveDays`、`returnAfterSignDays`、`shipOverdueDays`，整数，N 0–90、M 0–180、预警 1–30）；PRD 没给具体数值，默认 N = 3、M = 7、预警 3 天。修改只对之后新寄出、新签收的寄样单生效，已经填好的应寄回日期不会被追溯改动；单张寄样单仍可在寄出时手动指定，或事后用「延期」。接口为 `PUT /api/settings/:key`（白名单键 + 范围校验）。
- **延期（交叉合作）**：上一场样衣留给下一场用时，不产生退回，只把寄样单的应寄回日期延后，并强制填写说明；说明写进该次变更日志的来源（`延期：……`），所以在变更历史里能看到，也可以撤销。
- **回收问题次数由写后钩子自动累计**：退样明细的质检结果从"无/完好"变为任一问题类型（污渍、破损、缺配件、吊牌缺失、其他）时达人计数 +1，变回完好或明细被删除/撤销时 −1；后补填质检结果同样计数，已经是问题的明细再改成另一种问题不重复计。判断时忽略已软删除的行，所以撤销创建、撤销删除都能得到正确增减。
- **"质检待处理"** 定义为：退样明细还没质检（质检结果为空），或质检有问题但处理结果还没选。
- **清除收货地址**：只有在外为 0 时才允许（领域层校验），软删除该达人的全部收货地址，可在变更历史里撤销。
- **寄样单上的收件信息（收件人、手机、地址）是寄出时的快照**，API 返回时一律打码；寄出弹窗里为了让用户确认地址，会用「查看敏感信息」同一个 reveal 接口取默认地址的明文展示。
- **批量标记寄出**逐张独立处理：没有收货地址等失败的单张不影响其他，返回成功和失败列表。单次上限 200 张。
- **质检照片**通过 `POST /api/attachments/image` 上传（图片 ≤ 10 MB，JPG/PNG/WebP/GIF），退样明细只存附件 id 数组。
- **阶段 4 未做**：手动指定冲抵的寄出记录；寄样单的编辑（目前待寄样单只能删除重建）；PRD 5.1 首页的寄样预警汇总（阶段 5，数据接口已经有：逾期、质检待处理、待寄样天数）。

## 2026-10-18 阶段 5

## 2026-10-18 阶段 7：AI 助手的取舍

- **OCR 选型**：用虚构聊天截图实测三种本地方案。Windows 自带 OCR：零安装、约 0.5 秒，中文可用但汉字间会插空格、偶有错字（"佣金"→"佣全"）；PaddleOCR（@gutenye/ocr-node，ONNX）：7 行全部正确，约 1.2 秒，但依赖约 300 MB（onnxruntime）；tesseract.js：需联网下载 chi_sim 语言数据，离线环境无法运行，未评测准确率。**决定**：默认用 Windows 自带 OCR（`ai/ocr.ts`，引擎是可替换接口），识别结果先给用户核对、可修改，再发送；需要更高准确率时再新增 PaddleOCR 引擎实现。
- **外发网关 fail-closed**：Pi 会吞掉 `before_provider_request` 钩子里的异常并原样发出，所以适配层捕获异常后换成无意义载荷让请求失败，不放行原文。
- **提供方报错**：Pi 不抛异常而是在助手消息标记 error，适配层据此发出 error 事件（否则密钥错误会静默"完成"）。
- **AI 的修改一律走审核**（`EntityService.propose`）；新增跟进/草稿合作/寄样草稿直接写入并可撤销；金额、佣金、日期与原文由程序核对。
- **工具调用回归集**：`ai/regression/`（14 个用例 + 固定虚构数据）。`pnpm --filter @workbench/server ai:regress [用例id]` 对当前配置的真实模型跑一遍（临时数据库，配置复制自数据目录，跑完删除）；`regression.test.ts` 用本地假接口回放"理想脚本"和"坏模型"，证明用例自洽且能发现问题。
- **确认合作即确认其达人**：用户选中或确认了某个合作后，该合作的达人也算已确认（否则"选中合作后建寄样草稿"会被目标确认拦住）。
- **未验证**：真实 DeepSeek 调用（需用户在设置页填自己的 Key）；`suggest_import_mapping` 只以导入向导里的"AI 建议映射"按钮提供，没有放进聊天工具。
